RenderFlow

Distributed media processing platform. Built as a production-style portfolio project to demonstrate queues, worker reliability, containers, and Kubernetes.

GitHub repository View architecture

Problem

Transcoding and related FFmpeg work must run off the request path, survive failures, and scale horizontally—with operators able to inspect and retry jobs.

Solution

FastAPI accepts jobs; Redis backs the queue; workers claim work with heartbeats, retries, and idempotency keys; results land in object storage. Ops UI lists jobs/workers; Compose + Kubernetes manifests encode the deployment shape.

Architecture

React ops UI → FastAPI (jobs, workers, retries) → PostgreSQL (job records) → Redis queue → Worker pool (FFmpeg / mock fallback) → Object storage

Key features

  • Job types: transcode, thumbnail, audio extract, metadata
  • Status, priority, retries, error messages, idempotency
  • Worker heartbeat and failed-job retry
  • Docker Compose multi-service stack
  • Kubernetes Deployments, Services, ConfigMaps, Secrets, probes, HPA

Technical decisions

  • Job state machine explicit in DB + queue payloads
  • Idempotency keys prevent duplicate side effects on retry
  • Health/readiness probes separate liveness from dependency readiness
  • Mock processing path keeps CI green without FFmpeg

Challenges

  • At-least-once delivery vs. exactly-once side effects
  • Detecting dead workers via heartbeats
  • K8s manifests that are realistic without requiring a live cluster in CI

Testing

State machine, retry/idempotency, and API tests; container build in CI.

Infrastructure

Local Compose. K8s under k8s/. AWS sketch: EKS or ECS, ElastiCache/SQS, S3, RDS. Health endpoints feed load balancer and orchestrator probes.

What I learned

Distributed media work is operations work: heartbeats, retries, and probes are product features for reliability—not afterthoughts.
