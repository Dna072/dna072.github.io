Executive Summary

Music streaming platforms generate continuous streams of user activity and catalog metadata. Without a reliable warehouse pipeline, product, growth, and data science teams are forced to query raw JSON logs — slow, inconsistent, and unsuitable for recurring analytics.

This project delivers an end-to-end cloud data warehouse pipeline that:

Business Need How This Pipeline Addresses It
Trusted listening analytics Transforms raw events into a curated songplays fact table
Consistent dimensional context Maintains user, song, artist, and time dimensions
Operational reliability Orchestrates ETL with Airflow retries, logging, and quality gates
Analyst-ready data Exposes a star schema optimized for BI and ad-hoc SQL

Value generated

  • Faster time-to-insight — analysts query dimensional models instead of nested JSON
  • Lower operational risk — automated quality checks fail the pipeline when row counts or null constraints break expectations
  • Reusable engineering patterns — custom Airflow operators encapsulate staging, fact loads, dimension loads, and validation
  • Cloud-native scale — S3 as the landing zone and Redshift COPY for bulk parallel ingest

Built as a production-style reference implementation for engineering managers and hiring teams evaluating data platform design skills.

Data Model

The warehouse follows a classic star schema: one central fact table surrounded by denormalized dimensions. This pattern is chosen for music streaming analytics because:

  1. Songplays are the grain of business questions — “who listened to what, when, and where”
  2. Dimensions change slowly relative to event volume
  3. BI tools and SQL analysts join efficiently from a single fact out to descriptive attributes
  4. Quality checks can target null keys and expected entity counts per dimension

Fact Table

Table Grain Description
fact_songplays_table One row per NextSong play event Built by joining staged events to song metadata on title, artist, and duration; surrogate songplay_id derived via md5(sessionid || start_time)

Dimension Tables

Table Source Description
dim_users_table Staging events Distinct listeners and subscription level
dim_songs_table Staging songs Track catalog attributes
dim_artists_table Staging songs Artist identity and geo attributes
dim_time_table Fact songplays Calendar breakdown (hour, day, week, month, year, weekday) for time-series analysis

Staging Tables

Table Purpose
staging_events Landing zone for application JSON logs (DISTSTYLE EVEN)
staging_songs Landing zone for song catalog JSON (DISTSTYLE EVEN)

DDL for the logical warehouse schema also lives in create_tables.sql. Runtime loads create analytics tables via operator-driven CREATE TABLE … AS patterns (fact_* / dim_* naming).

Pipeline Workflow

The DAG (final_project) runs on an hourly schedule (0 * * * *) with parallel staging, a fact load bottleneck, fan-out dimension loads, and a terminal quality gate.

flowchart LR
    A[Begin execution] --> B[Stage events<br/>S3 → Redshift]
    A --> C[Stage songs<br/>S3 → Redshift]
    B --> D[Load songplays fact]
    C --> D
    D --> E[Load users dim]
    D --> F[Load songs dim]
    D --> G[Load artists dim]
    D --> H[Load time dim]
    E --> I[Data quality checks]
    F --> I
    G --> I
    H --> I
    I --> J[Stop execution]

Stage-by-stage walkthrough

Stage Operator What happens
1. Begin DummyOperator Marks DAG start
2. Stage Events StageToRedshiftOperator Drops/recreates staging_events, COPY from s3://{bucket}/log-data using a JSONPaths file
3. Stage Songs StageToRedshiftOperator Drops/recreates staging_songs, COPY from s3://{bucket}/song-data with FORMAT AS JSON 'auto'
4. Load Fact LoadFactOperator Builds fact_songplays_table from NextSong events left-joined to songs
5. Load Dimensions LoadDimensionOperator × 4 Rebuilds user, song, artist, and time dimensions (default truncate-insert / delete-load)
6. Quality Gate DataQualityOperator Runs SQL assertions (null checks + expected counts); fails the task on mismatch
7. Stop DummyOperator Marks successful completion

Source datasets

Dataset Format Partitioning Notes
Event logs JSON year/month path layout Simulated streaming app activity
Song metadata JSON Track-ID prefix paths Subset of the Million Song Dataset
Log JSONPaths JSON Single file Guides Redshift JSON parsing for event columns

Performance Considerations

Technique How it is applied
Parallel processing Independent staging tasks run in parallel; dimension loads fan out after the fact table is ready
Redshift COPY Bulk ingest from S3 — preferred over row-by-row inserts for warehouse loads
EVEN distribution on staging DISTSTYLE EVEN on staging tables spreads temporary load work evenly across slices
Source partitioning awareness Log data is organized by year/month; song data by track-ID prefixes — stage keys can be templated for narrower reads during backfills
Star schema query shape Fact + dimension design reduces wide JSON scans for common analytical questions
Celery workers Local Compose stack uses CeleryExecutor so tasks can execute across worker processes

Optimization opportunities (not yet hardcoded in runtime CTAS tables)

For larger production datasets, the next performance pass would typically add:

  • Distribution keys on high-cardinality join columns (e.g., userid, songid) for the fact table
  • Sort keys on start_time to accelerate time-range filters and merges
  • Selective incremental loads using execution-date-scoped S3 prefixes instead of full-prefix copies every run

Running Locally

Prerequisites

  • Docker Desktop (or Docker Engine + Compose)
  • An AWS account with:
    • IAM user/keys with S3 read access and Redshift access
    • An Amazon Redshift (Serverless or provisioned) endpoint
    • An S3 bucket containing log-data/, song-data/, and log_json_path.json
  • Recommended resources for the Compose stack: ≥ 4 GB RAM, ≥ 2 CPUs

1. Clone and configure environment

git clone https://github.com/Dna072/airflow-pipelines.git
cd airflow-pipelines
cp env.template .env

Fill in .env with your AWS keys, Redshift host/login/password, and S3 bucket name.

2. Prepare source data in S3

Place (or copy) the event logs, song metadata, and JSONPaths file into your bucket:

s3://<your-bucket>/log-data/
s3://<your-bucket>/song-data/
s3://<your-bucket>/log_json_path.json

Prefer colocating the bucket in the same AWS region as Redshift to reduce transfer cost and latency.

3. Start the Airflow stack

docker-compose --env-file .env up -d

Open the UI: http://localhost:8080
Default credentials: airflow / airflow

4. Configure Airflow connections & variables

Copy the template and set your URIs / bucket:

cp set_connections_and_variables.template set_connections_and_variables.sh
# edit aws_credentials URI, redshift URI, and s3_bucket
docker compose exec --user airflow airflow-webserver sh set_connections_and_variables.sh

Alternatively, configure via Admin → Connections / Variables in the UI:

Conn / Variable Purpose
aws_credentials AWS access for S3 COPY
redshift Warehouse connectivity
s3_bucket Source bucket name

5. Ensure Redshift is available and run the DAG

  1. Start/resume your Redshift workgroup or cluster
  2. Unpause and trigger the final_project DAG
  3. Confirm all tasks succeed through the quality gate

Optional: Flower (Celery monitoring)

docker-compose --env-file .env --profile flower up -d

Flower UI: http://localhost:5555

Future Improvements

Realistic production hardening paths for this codebase:

Area Improvement
CI/CD GitHub Actions for linting, DAG parse checks, and image builds on every PR
Infrastructure as Code Terraform/CDK for Redshift, S3, IAM roles, and networking
Transformation layer Adopt dbt for versioned models, docs, and lineage on top of staging tables
Data quality Expand beyond row-count asserts with Great Expectations or custom anomaly detection
Observability Metrics + alerts (task SLA misses, COPY failures); OpenLineage for end-to-end lineage
Data contracts Explicit schemas between producers (app logs / catalog) and the warehouse
Security Replace long-lived access keys with IAM roles / temporary credentials; secret backends (AWS Secrets Manager)
Incremental loading Execution-date-scoped S3 prefixes + append/merge patterns for facts at scale
Warehouse tuning Explicit DISTKEY / SORTKEY strategy on fact and large dimensions
Testing Unit tests for operators; integration tests against a disposable Redshift/local Postgres double

Lessons Learned

Decision Tradeoff
Custom operators over inline PythonOperators More upfront structure; much better reuse, testing surface, and DAG readability
Star schema over wide staging tables for analytics Extra transform step; dramatically clearer BI queries and dimensional quality checks
Delete-load dimensions by default Simple idempotency for moderate volumes; append/SCD patterns needed as dimensions grow
Fact rebuilt via CTAS each run Clean snapshots and easy local demos; not ideal for very large historical facts without incremental design
Airflow connections for credentials Convenient for local Compose; production should prefer IAM roles and a secrets backend
EVEN distribution on staging Fair for temporary tables; analytical tables need join-aware distribution at scale
SQL assertion quality checks Fast feedback and clear failure modes; complements (does not replace) statistical or schema-contract testing
CeleryExecutor locally Closer to production Airflow topology; heavier than LocalExecutor for laptop demos

The core engineering lesson: orchestration quality matters as much as SQL quality. Retries, explicit dependencies, reusable operators, and a hard quality gate turn a script into a pipeline teams can operate.
