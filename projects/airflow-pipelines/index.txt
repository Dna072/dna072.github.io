<p>Music streaming platforms generate continuous streams of user activity and catalog metadata. Without a reliable warehouse pipeline, product, growth, and data science teams are forced to query raw JSON logs — slow, inconsistent, and unsuitable for recurring analytics.</p>
<p>This project delivers an <strong>end-to-end cloud data warehouse pipeline</strong> that:</p>
<table>
<thead>
<tr>
<th>Business Need</th>
<th>How This Pipeline Addresses It</th>
</tr>
</thead>
<tbody>
<tr>
<td>Trusted listening analytics</td>
<td>Transforms raw events into a curated <code>songplays</code> fact table</td>
</tr>
<tr>
<td>Consistent dimensional context</td>
<td>Maintains user, song, artist, and time dimensions</td>
</tr>
<tr>
<td>Operational reliability</td>
<td>Orchestrates ETL with Airflow retries, logging, and quality gates</td>
</tr>
<tr>
<td>Analyst-ready data</td>
<td>Exposes a star schema optimized for BI and ad-hoc SQL</td>
</tr>
</tbody>
</table>
<p><strong>Value generated</strong></p>
<ul>
<li><strong>Faster time-to-insight</strong> — analysts query dimensional models instead of nested JSON</li>
<li><strong>Lower operational risk</strong> — automated quality checks fail the pipeline when row counts or null constraints break expectations</li>
<li><strong>Reusable engineering patterns</strong> — custom Airflow operators encapsulate staging, fact loads, dimension loads, and validation</li>
<li><strong>Cloud-native scale</strong> — S3 as the landing zone and Redshift <code>COPY</code> for bulk parallel ingest</li>
</ul>
<p>Built as a production-style reference implementation for engineering managers and hiring teams evaluating data platform design skills.</p>

<h2>Architecture</h2>
<pre><code class="language-mermaid">flowchart TB
    subgraph Sources["Source Systems"]
        APP["Music App Event Logs&#x3C;br/>(JSON, partitioned by year/month)"]
        CAT["Song Catalog Metadata&#x3C;br/>(JSON, Million Song Dataset subset)"]
    end

    subgraph Lake["Object Storage"]
        S3["Amazon S3&#x3C;br/>log-data / song-data / JSONPaths"]
    end

    subgraph Orchestration["Orchestration Layer"]
        AF["Apache Airflow 2.6&#x3C;br/>CeleryExecutor · Docker Compose"]
        PG["PostgreSQL&#x3C;br/>Airflow Metadata"]
        REDIS["Redis&#x3C;br/>Celery Broker"]
    end

    subgraph Warehouse["Analytics Warehouse — Amazon Redshift"]
        STG["Staging Layer&#x3C;br/>staging_events · staging_songs"]
        XFORM["Transformation Layer&#x3C;br/>Custom Operators + SQL"]
        STAR["Star Schema&#x3C;br/>fact_songplays + dimensions"]
    end

    subgraph Consumers["Downstream"]
        BI["BI / Reporting / Ad-hoc SQL"]
    end

    APP --> S3
    CAT --> S3
    S3 -->|"Redshift COPY"| STG
    AF --> STG
    AF --> XFORM
    AF --> STAR
    PG -.-> AF
    REDIS -.-> AF
    STG --> XFORM --> STAR --> BI
</code></pre>
<p><strong>Design intent:</strong> keep raw data immutable in S3, stage into Redshift for bulk load throughput, transform into analytics-friendly tables, and gate publication with SQL-based quality checks before the DAG completes.</p>

<h2>Data Model</h2>
<p>The warehouse follows a classic <strong>star schema</strong>: one central fact table surrounded by denormalized dimensions. This pattern is chosen for music streaming analytics because:</p>
<ol>
<li><strong>Songplays are the grain of business questions</strong> — “who listened to what, when, and where”</li>
<li><strong>Dimensions change slowly</strong> relative to event volume</li>
<li><strong>BI tools and SQL analysts</strong> join efficiently from a single fact out to descriptive attributes</li>
<li><strong>Quality checks</strong> can target null keys and expected entity counts per dimension</li>
</ol>
<pre><code class="language-mermaid">erDiagram
    FACT_SONGPLAYS ||--o{ DIM_USERS : "userid"
    FACT_SONGPLAYS ||--o{ DIM_SONGS : "songid"
    FACT_SONGPLAYS ||--o{ DIM_ARTISTS : "artistid"
    FACT_SONGPLAYS ||--o{ DIM_TIME : "start_time"

    FACT_SONGPLAYS {
        varchar playid PK
        timestamp start_time
        int userid
        varchar level
        varchar songid
        varchar artistid
        int sessionid
        varchar location
        varchar user_agent
    }

    DIM_USERS {
        int userid PK
        varchar first_name
        varchar last_name
        varchar gender
        varchar level
    }

    DIM_SONGS {
        varchar songid PK
        varchar title
        varchar artistid
        int year
        numeric duration
    }

    DIM_ARTISTS {
        varchar artistid PK
        varchar name
        varchar location
        numeric latitude
        numeric longitude
    }

    DIM_TIME {
        timestamp start_time PK
        int hour
        int day
        int week
        varchar month
        int year
        varchar weekday
    }
</code></pre>

<h2>Pipeline Workflow</h2>
<p>The DAG (<code>final_project</code>) runs on an <strong>hourly schedule</strong> (<code>0 * * * *</code>) with parallel staging, a fact load bottleneck, fan-out dimension loads, and a terminal quality gate.</p>
<pre><code class="language-mermaid">flowchart LR
    A[Begin execution] --> B[Stage events&#x3C;br/>S3 → Redshift]
    A --> C[Stage songs&#x3C;br/>S3 → Redshift]
    B --> D[Load songplays fact]
    C --> D
    D --> E[Load users dim]
    D --> F[Load songs dim]
    D --> G[Load artists dim]
    D --> H[Load time dim]
    E --> I[Data quality checks]
    F --> I
    G --> I
    H --> I
    I --> J[Stop execution]
</code></pre>
<h3>Stage-by-stage walkthrough</h3>
<table>
<thead>
<tr>
<th>Stage</th>
<th>Operator</th>
<th>What happens</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>1. Begin</strong></td>
<td><code>DummyOperator</code></td>
<td>Marks DAG start</td>
</tr>
<tr>
<td><strong>2. Stage Events</strong></td>
<td><code>StageToRedshiftOperator</code></td>
<td>Drops/recreates <code>staging_events</code>, <code>COPY</code> from <code>s3://{bucket}/log-data</code> using a JSONPaths file</td>
</tr>
<tr>
<td><strong>3. Stage Songs</strong></td>
<td><code>StageToRedshiftOperator</code></td>
<td>Drops/recreates <code>staging_songs</code>, <code>COPY</code> from <code>s3://{bucket}/song-data</code> with <code>FORMAT AS JSON 'auto'</code></td>
</tr>
<tr>
<td><strong>4. Load Fact</strong></td>
<td><code>LoadFactOperator</code></td>
<td>Builds <code>fact_songplays_table</code> from <code>NextSong</code> events left-joined to songs</td>
</tr>
<tr>
<td><strong>5. Load Dimensions</strong></td>
<td><code>LoadDimensionOperator</code> × 4</td>
<td>Rebuilds user, song, artist, and time dimensions (default truncate-insert / delete-load)</td>
</tr>
<tr>
<td><strong>6. Quality Gate</strong></td>
<td><code>DataQualityOperator</code></td>
<td>Runs SQL assertions (null checks + expected counts); fails the task on mismatch</td>
</tr>
<tr>
<td><strong>7. Stop</strong></td>
<td><code>DummyOperator</code></td>
<td>Marks successful completion</td>
</tr>
</tbody>

<h2>Performance Considerations</h2>
<table>
<thead>
<tr>
<th>Technique</th>
<th>How it is applied</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Parallel processing</strong></td>
<td>Independent staging tasks run in parallel; dimension loads fan out after the fact table is ready</td>
</tr>
<tr>
<td><strong>Redshift <code>COPY</code></strong></td>
<td>Bulk ingest from S3 — preferred over row-by-row inserts for warehouse loads</td>
</tr>
<tr>
<td><strong>EVEN distribution on staging</strong></td>
<td><code>DISTSTYLE EVEN</code> on staging tables spreads temporary load work evenly across slices</td>
</tr>
<tr>
<td><strong>Source partitioning awareness</strong></td>
<td>Log data is organized by year/month; song data by track-ID prefixes — stage keys can be templated for narrower reads during backfills</td>
</tr>
<tr>
<td><strong>Star schema query shape</strong></td>
<td>Fact + dimension design reduces wide JSON scans for common analytical questions</td>
</tr>
<tr>
<td><strong>Celery workers</strong></td>
<td>Local Compose stack uses CeleryExecutor so tasks can execute across worker processes</td>
</tr>
</tbody>
</table>
<h3>Optimization opportunities (not yet hardcoded in runtime CTAS tables)</h3>
<p>For larger production datasets, the next performance pass would typically add:</p>
<ul>
<li><strong>Distribution keys</strong> on high-cardinality join columns (e.g., <code>userid</code>, <code>songid</code>) for the fact table</li>
<li><strong>Sort keys</strong> on <code>start_time</code> to accelerate time-range filters and merges</li>
<li><strong>Selective incremental loads</strong> using execution-date-scoped S3 prefixes instead of full-prefix copies every run</li>
</ul>

<h2>Running Locally</h2>
<h3>Prerequisites</h3>
<ul>
<li>Docker Desktop (or Docker Engine + Compose)</li>
<li>An AWS account with:
<ul>
<li>IAM user/keys with S3 read access and Redshift access</li>
<li>An Amazon Redshift (Serverless or provisioned) endpoint</li>
<li>An S3 bucket containing <code>log-data/</code>, <code>song-data/</code>, and <code>log_json_path.json</code></li>
</ul>
</li>
<li>Recommended resources for the Compose stack: <strong>≥ 4 GB RAM</strong>, <strong>≥ 2 CPUs</strong></li>
</ul>
<h3>1. Clone and configure environment</h3>
<pre><code class="language-bash">git clone https://github.com/Dna072/airflow-pipelines.git
cd airflow-pipelines
cp env.template .env
</code></pre>
<p>Fill in <code>.env</code> with your AWS keys, Redshift host/login/password, and S3 bucket name.</p>
<h3>2. Prepare source data in S3</h3>
<p>Place (or copy) the event logs, song metadata, and JSONPaths file into your bucket:</p>
<pre><code class="language-text">s3://&#x3C;your-bucket>/log-data/
s3://&#x3C;your-bucket>/song-data/
s3://&#x3C;your-bucket>/log_json_path.json
</code></pre>
<blockquote>
<p>Prefer colocating the bucket in the <strong>same AWS region</strong> as Redshift to reduce transfer cost and latency.</p>
</blockquote>
<h3>3. Start the Airflow stack</h3>
<pre><code class="language-bash">docker-compose --env-file .env up -d
</code></pre>
<p>Open the UI: <a href="http://localhost:8080">http://localhost:8080</a><br>
Default credentials: <code>airflow</code> / <code>airflow</code></p>
<h3>4. Configure Airflow connections &#x26; variables</h3>
<p>Copy the template and set your URIs / bucket:</p>
<pre><code class="language-bash">cp set_connections_and_variables.template set_connections_and_variables.sh
# edit aws_credentials URI, redshift URI, and s3_bucket
docker compose exec --user airflow airflow-webserver sh set_connections_and_variables.sh
</code></pre>
<p>Alternatively, configure via <strong>Admin → Connections / Variables</strong> in the UI:</p>
<table>
<thead>
<tr>
<th>Conn / Variable</th>
<th>Purpose</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>aws_credentials</code></td>
<td>AWS access for S3 <code>COPY</code></td>
</tr>
<tr>
<td><code>redshift</code></td>
<td>Warehouse connectivity</td>
</tr>
<tr>
<td><code>s3_bucket</code></td>
<td>Source bucket name</td>
</tr>
</tbody>
</table>
<h3>5. Ensure Redshift is available and run the DAG</h3>
<ol>
<li>Start/resume your Redshift workgroup or cluster</li>
<li>Unpause and trigger the <code>final_project</code> DAG</li>
<li>Confirm all tasks succeed through the quality gate</li>
</ol>
<h3>Optional: Flower (Celery monitoring)</h3>
<pre><code class="language-bash">docker-compose --env-file .env --profile flower up -d
</code></pre>
<p>Flower UI: <a href="http://localhost:5555">http://localhost:5555</a></p>

<h2>Lessons Learned</h2>
<table>
<thead>
<tr>
<th>Decision</th>
<th>Tradeoff</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Custom operators over inline PythonOperators</strong></td>
<td>More upfront structure; much better reuse, testing surface, and DAG readability</td>
</tr>
<tr>
<td><strong>Star schema over wide staging tables for analytics</strong></td>
<td>Extra transform step; dramatically clearer BI queries and dimensional quality checks</td>
</tr>
<tr>
<td><strong>Delete-load dimensions by default</strong></td>
<td>Simple idempotency for moderate volumes; append/SCD patterns needed as dimensions grow</td>
</tr>
<tr>
<td><strong>Fact rebuilt via CTAS each run</strong></td>
<td>Clean snapshots and easy local demos; not ideal for very large historical facts without incremental design</td>
</tr>
<tr>
<td><strong>Airflow connections for credentials</strong></td>
<td>Convenient for local Compose; production should prefer IAM roles and a secrets backend</td>
</tr>
<tr>
<td><strong>EVEN distribution on staging</strong></td>
<td>Fair for temporary tables; analytical tables need join-aware distribution at scale</td>
</tr>
<tr>
<td><strong>SQL assertion quality checks</strong></td>
<td>Fast feedback and clear failure modes; complements (does not replace) statistical or schema-contract testing</td>
</tr>
<tr>
<td><strong>CeleryExecutor locally</strong></td>
<td>Closer to production Airflow topology; heavier than LocalExecutor for laptop demos</td>
</tr>
</tbody>
</table>
<p>The core engineering lesson: <strong>orchestration quality matters as much as SQL quality</strong>. Retries, explicit dependencies, reusable operators, and a hard quality gate turn a script into a pipeline teams can operate.</p>
