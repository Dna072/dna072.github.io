22:T52da,<h1>RenderFlow — Distributed Media Processing Platform</h1>
<p>RenderFlow is a production-style distributed system for processing media at
scale: submit a job (transcode, thumbnail, audio extraction, metadata probe),
and a pool of horizontally-scalable workers pulls it off a priority queue,
runs it with FFmpeg, stores the result, and reports status — with automatic
retries, idempotent submission, worker heartbeats, structured logs, and health
probes wired for Kubernetes.</p>
<blockquote>
<p><strong>Honesty note:</strong> This is a portfolio project built to demonstrate backend and
infrastructure engineering. It ships with real, working code and tests, but it
is <strong>not</strong> running production traffic — there are no real users, uptime, or
revenue claims. Benchmarks (if any) are local test results only.</p>
</blockquote>

<h2>Job lifecycle (state machine)</h2>
<p>Transitions are enforced centrally in <a href="backend/app/state_machine.py"><code>app/state_machine.py</code></a>;
any illegal transition raises rather than silently corrupting state.</p>
<pre><code class="language-mermaid">stateDiagram-v2
    [*] --> pending
    pending --> queued: enqueue
    queued --> running: worker claims (lease)
    running --> succeeded: processed OK
    running --> retrying: failed, retries left
    retrying --> queued: backoff elapsed → re-enqueue
    running --> failed: retries exhausted
    queued --> cancelled: operator
    running --> cancelled: operator
    failed --> queued: operator retry
    cancelled --> queued: operator retry
    running --> queued: reaper (lease expired)
    succeeded --> [*]
    failed --> [*]
    cancelled --> [*]
</code></pre>
<p>Terminal states: <code>succeeded</code>, <code>failed</code>, <code>cancelled</code>. <code>succeeded</code> is fully
terminal; <code>failed</code>/<code>cancelled</code> can be manually re-queued by an operator.</p>

<h2>Reliability features</h2>
<h3>Idempotent submission</h3>
<p>Clients may pass an <code>idempotency_key</code>. A DB unique constraint plus a
check-then-insert (with an <code>IntegrityError</code> fallback for the race) guarantees a
retried submission returns the <strong>same</strong> job instead of spawning duplicate work.</p>
<h3>Retry with exponential backoff</h3>
<p>On failure a job's <code>retries</code> counter increments. While <code>retries &#x3C;= max_retries</code>
the job moves to <code>retrying</code> and is re-enqueued with a delay of
<code>base ** attempt</code> seconds (capped, plus jitter). The Redis queue schedules the
delay natively (the job simply isn't returned until its scheduled time). Once the
budget is exhausted the job becomes terminally <code>failed</code> and appears in
<code>/jobs/failed</code> for inspection and manual retry.</p>
<h3>Worker heartbeats &#x26; the reaper</h3>
<p>Each worker writes a heartbeat (state, current job, counters) to the DB on a
timer. The dashboard shows online/offline status. If a worker dies mid-job, its
job stays <code>running</code> with an expired <strong>lease</strong> — a background reaper thread in the
API detects the expired lease and requeues the job (subject to the same retry
rules), so no work is lost to a crashed pod.</p>
<hr>
<h2>Health probes in production</h2>
<p>RenderFlow exposes two distinct probes because <em>liveness</em> and <em>readiness</em> answer
different questions — conflating them is a classic cause of cascading outages.</p>
<p><strong><code>GET /health</code> — liveness.</strong> Cheap and dependency-free. It only asserts the
process itself is responsive. Kubernetes uses it as <code>livenessProbe</code>: if it stops
returning <code>200</code>, the process is wedged and the pod is <strong>restarted</strong>. Crucially it
does <em>not</em> check the database or Redis — otherwise a brief DB blip would make
Kubernetes kill every API pod at once, turning a recoverable dependency hiccup
into a full outage.</p>
<p><strong><code>GET /ready</code> — readiness.</strong> Verifies the pod can actually serve traffic by
checking the database (<code>SELECT 1</code>) and the queue (<code>PING</code>). It returns <code>503</code> when
a dependency is unreachable. Kubernetes uses it as <code>readinessProbe</code>: a failing
pod is <strong>removed from the Service endpoints</strong> (no traffic routed to it) but <strong>not
restarted</strong>. When the dependency recovers, the pod re-enters rotation
automatically. This drains traffic gracefully during dependency outages and
during rollouts (a new pod only receives traffic once it's genuinely ready).</p>
<p><strong><code>startupProbe</code>.</strong> The API also defines a startup probe so slow first-boot work
(e.g. migrations) doesn't trip the liveness probe and cause a restart loop.</p>
<p><strong>Workers</strong> have no HTTP server, so their liveness is file-based: the worker
touches <code>RENDERFLOW_WORKER_LIVENESS_FILE</code> on every heartbeat, and the Kubernetes
<code>livenessProbe</code> execs a check that the file was updated within the heartbeat
window. A hung worker whose loop stalls stops touching the file and is restarted.</p>
<p>See the probe definitions in
<a href="k8s/api-deployment.yaml"><code>k8s/api-deployment.yaml</code></a> and
<a href="k8s/worker-deployment.yaml"><code>k8s/worker-deployment.yaml</code></a>.</p>

<ul>
<li><strong>Structured logging:</strong> every log line is JSON (<code>app/logging_config.py</code>) with

<h2>Design decisions &#x26; trade-offs</h2>
<ul>
<li><strong>Redis sorted-set as the queue</strong> (vs. a list): a single structure gives us
both priority ordering <em>and</em> delayed delivery for backoff, with an atomic
Lua-scripted "pop earliest ready" so concurrent workers never double-claim.</li>
<li><strong>DB-backed leases + reaper</strong> (vs. Redis visibility timeouts): keeps the
authoritative job state in one place (Postgres) and makes crash recovery
explicit and testable.</li>
<li><strong>All mutations through a service layer</strong> that validates every transition:
the queue, API, worker, and reaper can't drift into inconsistent state.</li>
<li><strong>Pluggable storage/queue</strong> behind interfaces: SQLite + in-process queue for
fast, hermetic tests; Postgres + Redis for real deployments — no code change.</li>
<li><strong>Mock processing fallback:</strong> the pipeline is exercisable in CI without FFmpeg.</li>
</ul>
<hr>
<h2>Limitations &#x26; roadmap</h2>
<ul>
<li>Schema is created via <code>create_all</code> for demo simplicity; a real deployment
would use <strong>Alembic</strong> migrations.</li>
<li>Queue-depth autoscaling is documented (KEDA) but not wired — the shipped HPA
scales on CPU.</li>
<li>No authentication on the API — an API gateway / auth layer would front it in
production.</li>
<li>Metrics are via structured logs; a <code>/metrics</code> Prometheus endpoint is a natural
next step.</li>
</ul>
