Enterprise Cloud Data Warehouse for Music Streaming Analytics

A production-oriented ETL pipeline that ingests music streaming event logs and song metadata from S3, stages them in Amazon Redshift, and transforms them into a star-schema analytics warehouse.

Architecture · Data Model · Pipeline Workflow · Running Locally · Future Improvements

Executive Summary

Music streaming platforms generate high-volume, semi-structured event data — page views, session activity, and playback events — alongside structured catalog metadata for songs and artists. Product, analytics, and growth teams need a reliable way to answer questions like Which songs drive the most engagement?, Who are the most active listeners?, and How does listening behavior vary by geography and time of day?

Raw JSON logs in object storage are not optimized for analytical workloads. Ad-hoc queries against S3 are slow, expensive, and difficult to govern. Organizations solve this by building ELT pipelines that land data in a columnar cloud data warehouse, apply dimensional modeling, and expose curated tables to BI tools and data scientists.

This project implements that pattern end-to-end:

Outcome Business Value
Curated star-schema warehouse Fast, predictable SQL for product and analytics teams
Automated S3 → Redshift ingestion Eliminates manual data movement and reduces operational toil
Infrastructure provisioning via code Repeatable cluster and IAM setup across environments
Distribution and sort key tuning Query performance aligned with common analytical access patterns

I designed and built this pipeline to demonstrate how I approach cloud data warehouse engineering: schema design driven by query patterns, infrastructure automation, and performance-conscious Redshift physical design.

Data Model

I selected a star schema because the primary access pattern is analytical: aggregations and filters over song play events joined to descriptive dimensions. Star schemas minimize join complexity, align with BI tool expectations, and map cleanly to Redshift's MPP query planner.

Fact Table

fact_songplays — one row per song play event (grain: individual playback).

Column Description
songplay_id Surrogate key (IDENTITY)
start_time Event timestamp — sort key for time-range queries
user_id Listener reference
level Subscription tier at time of play (free / paid)
song_id, artist_id Catalog references
session_id Application session identifier
location Listener metro area
user_agent Client browser / device string

Only events where page = 'NextSong' and user_id IS NOT NULL are loaded, ensuring the fact table captures confirmed playback actions.

Dimension Tables

Table Purpose Key Design Choice
dim_users Listener attributes (name, gender, subscription level) DISTSTYLE ALL — small table replicated to every slice for co-located joins
dim_songs Song metadata (title, year, duration) DISTKEY artist_id — balanced distribution; SORTKEY title for title searches
dim_artists Artist metadata including geolocation DISTSTYLE AUTO — avoids manual skew on high-cardinality keys
dim_times Timestamp decomposed into hour, day, week, month, year, weekday SORTKEY start_time — accelerates time-based filtering and grouping

Staging Tables

Table Source Purpose
staging_events S3 event logs Raw JSON parsed via JSONPath manifest
staging_songs S3 song metadata Raw catalog records (FORMAT AS JSON 'auto')

Both use DISTSTYLE EVEN — they are transient load targets, not join-optimized analytics tables.

Why Star Schema?

Alternative Tradeoff My Decision
Snowflake schema Normalized dimensions reduce redundancy but increase join depth Rejected — dimension tables are small; denormalization cost is negligible
Wide denormalized table Simple queries but massive redundancy and update anomalies Rejected — poor fit for evolving catalog metadata
Star schema Fast aggregations, intuitive for analysts, Redshift-optimized Selected — matches query patterns and team skill sets

Stage 1 — Infrastructure Provisioning

redshift_setup.py automates the AWS footprint:

  1. IAM role — created (or retrieved) with AmazonS3ReadOnlyAccess, trusted by redshift.amazonaws.com
  2. Redshift cluster — provisioned with configurable node type, node count, and attached IAM role
  3. Network access — security group ingress opened on port 5439
  4. Health check — connection validated via psycopg2
python redshift_setup.py --create   # Provision cluster
python redshift_setup.py --test     # Verify connectivity
python redshift_setup.py --delete   # Tear down cluster

Stage 2 — Schema Initialization

create_tables.py performs an idempotent full reset of the warehouse schema:

  1. Drop all staging and analytics tables (if they exist)
  2. Create tables in dependency order: dimensions first, then the fact table

All DDL lives in sql_queries.py as parameterized query strings — a single source of truth for schema and ETL logic.

Stage 3 — Extract & Load (Staging)

etl.py executes parallel S3 COPY commands:

Target S3 Source Format
staging_events s3://…/log_data JSON with explicit JSONPath manifest
staging_songs s3://…/song_data JSON auto-detection

Redshift's COPY command leverages the cluster's MPP architecture to load data in parallel directly from S3.

Stage 4 — Transform (Analytics Tables)

SQL INSERT … SELECT statements populate the star schema:

  • dim_users — DISTINCT on user_id, ordered by ts DESC to retain the most recent user attributes
  • dim_songs / dim_artists — loaded from song metadata staging
  • dim_times — timestamps converted from epoch milliseconds and decomposed with EXTRACT
  • fact_songplays — inner join of staging_events and staging_songs on song title + artist name, filtered to NextSong page events

Stage 5 — Validation & Analytics

  • stl_load_errors.py — inspects Redshift's stl_load_errors system table for COPY failures
  • example_queries.py — runs five analytical queries with execution timing

Performance Considerations

Redshift performance depends on how data is physically laid out across nodes (slices). I made deliberate choices for each table class:

Distribution Keys

Strategy Applied To Rationale
DISTSTYLE ALL dim_users Small dimension replicated on every slice — eliminates redistribution during fact joins
DISTKEY dim_songs (artist_id) Co-locates songs with their artists; relatively balanced cardinality
DISTSTYLE AUTO fact_songplays, dim_artists, dim_times Delegates to Redshift's optimizer to avoid manual skew
DISTSTYLE EVEN Staging tables Simple round-robin for transient data not involved in complex joins

Sort Keys

Table Sort Key Query Pattern Served
fact_songplays start_time Time-range filters, chronological ordering
dim_songs title Song title lookups and pattern searches
dim_artists artist_name Artist name ordering and filtering
dim_times start_time Time dimension joins and temporal grouping
dim_users user_id Point lookups by user

Parallel Processing

  • COPY from S3 — Redshift automatically parallelizes loads across slices, one file per slice where possible
  • MPP query execution — aggregation queries in example_queries.py benefit from zone-map pruning on sort keys after the first scan

Observed Query Performance

Sample results from a 4-node ra3.large cluster (first-run timings; subsequent queries benefit from cache):

Query Time
Top 10 locations by song plays ~0.3s
Most popular artists ~5.5s
Top 10 most played songs ~6.4s
Song plays by weekday ~6.7s
Top 10 most active users ~7.4s

Location aggregations on fact_songplays are fastest because they avoid multi-table joins. Dimensional joins pay a one-time compilation and cache-warming cost on first execution.

Running Locally

Prerequisites

  • Python 3.8+
  • AWS account with permissions for IAM, Redshift, EC2 (security groups), and S3 read access
  • Sample datasets accessible from your Redshift cluster's IAM role (public JSON logs and song metadata in S3)

1. Clone and install dependencies

git clone https://github.com/<your-username>/music-streaming-data-warehouse.git
cd music-streaming-data-warehouse

pip install -r requirements.txt

2. Configure credentials

Copy the example config and fill in your values:

cp dwh.cfg.example dwh.cfg

[AWS]
KEY=<your-aws-access-key-id>
SECRET=<your-aws-secret-access-key>

[DWH]
HOST=                          # Populated after cluster creation
DB_NAME=dev
DB_USER=awsuser
DB_PASSWORD=<strong-password>
DB_PORT=5439
DWH_CLUSTER_TYPE=single-node  # or multi-node
DWH_NUM_NODES=1
DWH_NODE_TYPE=ra3.large
DWH_IAM_ROLE_NAME=dwhRole
DWH_CLUSTER_IDENTIFIER=dwhCluster

[IAM_ROLE]
ARN=                           # Populated after IAM role creation

Security: dwh.cfg is gitignored. Never commit credentials to version control.

3. Provision infrastructure

python redshift_setup.py --create

Copy the printed IAM Role ARN and Cluster endpoint into dwh.cfg, then verify connectivity:

python redshift_setup.py --test

4. Create schema

python create_tables.py

5. Run the ETL pipeline

python etl.py

Expected output:

⏳ Loading staging tables...
⏳ Loading analytical tables...
✅ Done loading tables!

6. Validate and explore

# Check for COPY errors
python stl_load_errors.py

# Run analytical queries with timing
python example_queries.py

7. Tear down (avoid ongoing AWS charges)

python redshift_setup.py --delete

Lessons Learned

Staging before transforming

Loading raw JSON into staging tables before applying business logic was the right call. When a COPY failed due to JSONPath mismatches, I could inspect staging_events column metadata and stl_load_errors without corrupting analytics tables.

Distribution key selection requires data profiling

I initially considered distributing fact_songplays on user_id, but high-cardinality keys with skewed access patterns can create hot slices. I chose DISTSTYLE AUTO for the fact table and DISTKEY artist_id for songs after analyzing cardinality — letting Redshift optimize where manual tuning had unclear benefit.

Join logic is the highest-risk transformation

Linking event logs to song metadata via (song title, artist name) works for this dataset but is fragile in production. A production pipeline would join on stable surrogate keys (song_id) emitted by the application at event time.

Full reloads are fine until they aren't

Drop-and-reload simplifies development and guarantees consistency. At scale, I would introduce incremental loads keyed on event timestamp with merge semantics and late-arriving data handling.

Infrastructure automation saves hours

Provisioning a Redshift cluster, IAM role, and security group manually is error-prone. Codifying it in redshift_setup.py made teardown and re-creation repeatable — a pattern I'd extend with Terraform for team use.
