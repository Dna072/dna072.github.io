<hr>
<h2>Executive Summary</h2>
<p>Music streaming platforms generate high-volume, semi-structured event data — page views, session activity, and playback events — alongside structured catalog metadata for songs and artists. Product, analytics, and growth teams need a reliable way to answer questions like <em>Which songs drive the most engagement?</em>, <em>Who are the most active listeners?</em>, and <em>How does listening behavior vary by geography and time of day?</em></p>
<p>Raw JSON logs in object storage are not optimized for analytical workloads. Ad-hoc queries against S3 are slow, expensive, and difficult to govern. Organizations solve this by building <strong>ELT pipelines</strong> that land data in a columnar cloud data warehouse, apply dimensional modeling, and expose curated tables to BI tools and data scientists.</p>
<p>This project implements that pattern end-to-end:</p>

<h2>Data Model</h2>
<p>I selected a <strong>star schema</strong> because the primary access pattern is analytical: aggregations and filters over song play events joined to descriptive dimensions. Star schemas minimize join complexity, align with BI tool expectations, and map cleanly to Redshift's MPP query planner.</p>
<h3>Entity Relationship</h3>

<h2>Pipeline Workflow</h2>
<pre><code class="language-mermaid">sequenceDiagram
    participant Dev as Operator
    participant Setup as redshift_setup.py
    participant AWS as AWS APIs
    participant DDL as create_tables.py
    participant ETL as etl.py
    participant RS as Redshift

    Dev->>Setup: python redshift_setup.py --create
    Setup->>AWS: Create IAM role (S3ReadOnlyAccess)
    Setup->>AWS: Create Redshift cluster
    Setup->>AWS: Open security group port 5439
    Setup->>RS: Test psycopg2 connection

    Dev->>DDL: python create_tables.py
    DDL->>RS: DROP existing tables (if any)
    DDL->>RS: CREATE staging + dimension + fact tables

    Dev->>ETL: python etl.py
    ETL->>RS: COPY staging_events ← S3 log_data
    ETL->>RS: COPY staging_songs ← S3 song_data
    ETL->>RS: INSERT dim_users (deduplicated, latest record)
    ETL->>RS: INSERT dim_songs
    ETL->>RS: INSERT dim_artists (distinct)
    ETL->>RS: INSERT dim_times (timestamp decomposition)
    ETL->>RS: INSERT fact_songplays (staging join + filter)

    Dev->>RS: python example_queries.py
    RS-->>Dev: Analytics results + query timings

<h3>Stage 1 — Infrastructure Provisioning</h3>
<p><code>redshift_setup.py</code> automates the AWS footprint:</p>
<ol>
<li><strong>IAM role</strong> — created (or retrieved) with <code>AmazonS3ReadOnlyAccess</code>, trusted by <code>redshift.amazonaws.com</code></li>
<li><strong>Redshift cluster</strong> — provisioned with configurable node type, node count, and attached IAM role</li>
<li><strong>Network access</strong> — security group ingress opened on port <code>5439</code></li>
<li><strong>Health check</strong> — connection validated via <code>psycopg2</code></li>
</ol>
<pre><code class="language-bash">python redshift_setup.py --create   # Provision cluster
python redshift_setup.py --test     # Verify connectivity
python redshift_setup.py --delete   # Tear down cluster
</code></pre>
<h3>Stage 2 — Schema Initialization</h3>
<p><code>create_tables.py</code> performs an <strong>idempotent full reset</strong> of the warehouse schema:</p>
<ol>
<li>Drop all staging and analytics tables (if they exist)</li>
<li>Create tables in dependency order: dimensions first, then the fact table</li>
</ol>
<p>All DDL lives in <code>sql_queries.py</code> as parameterized query strings — a single source of truth for schema and ETL logic.</p>
<h3>Stage 3 — Extract &#x26; Load (Staging)</h3>
<p><code>etl.py</code> executes parallel S3 COPY commands:</p>
<table>
<thead>
<tr>
<th>Target</th>
<th>S3 Source</th>
<th>Format</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>staging_events</code></td>
<td><code>s3://…/log_data</code></td>
<td>JSON with explicit JSONPath manifest</td>
</tr>
<tr>
<td><code>staging_songs</code></td>
<td><code>s3://…/song_data</code></td>
<td>JSON auto-detection</td>
</tr>
</tbody>
</table>
<p>Redshift's COPY command leverages the cluster's MPP architecture to load data in parallel directly from S3.</p>
<h3>Stage 4 — Transform (Analytics Tables)</h3>
<p>SQL <code>INSERT … SELECT</code> statements populate the star schema:</p>
<ul>
<li><strong><code>dim_users</code></strong> — <code>DISTINCT</code> on <code>user_id</code>, ordered by <code>ts DESC</code> to retain the most recent user attributes</li>
<li><strong><code>dim_songs</code></strong> / <strong><code>dim_artists</code></strong> — loaded from song metadata staging</li>
<li><strong><code>dim_times</code></strong> — timestamps converted from epoch milliseconds and decomposed with <code>EXTRACT</code></li>
<li><strong><code>fact_songplays</code></strong> — inner join of <code>staging_events</code> and <code>staging_songs</code> on song title + artist name, filtered to <code>NextSong</code> page events</li>
</ul>
<h3>Stage 5 — Validation &#x26; Analytics</h3>
<ul>
<li><strong><code>stl_load_errors.py</code></strong> — inspects Redshift's <code>stl_load_errors</code> system table for COPY failures</li>
<li><strong><code>example_queries.py</code></strong> — runs five analytical queries with execution timing</li>
</ul>

<h2>Performance Considerations</h2>
<p>Redshift performance depends on how data is physically laid out across nodes (slices). I made deliberate choices for each table class:</p>
<h3>Distribution Keys</h3>
<table>
<thead>
<tr>
<th>Strategy</th>
<th>Applied To</th>
<th>Rationale</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>DISTSTYLE ALL</strong></td>
<td><code>dim_users</code></td>
<td>Small dimension replicated on every slice — eliminates redistribution during fact joins</td>
</tr>
<tr>
<td><strong>DISTKEY</strong></td>
<td><code>dim_songs</code> (<code>artist_id</code>)</td>
<td>Co-locates songs with their artists; relatively balanced cardinality</td>
</tr>
<tr>
<td><strong>DISTSTYLE AUTO</strong></td>
<td><code>fact_songplays</code>, <code>dim_artists</code>, <code>dim_times</code></td>
<td>Delegates to Redshift's optimizer to avoid manual skew</td>
</tr>
<tr>
<td><strong>DISTSTYLE EVEN</strong></td>
<td>Staging tables</td>
<td>Simple round-robin for transient data not involved in complex joins</td>
</tr>
</tbody>
</table>

<h2>Lessons Learned</h2>
<h3>Staging before transforming</h3>
<p>Loading raw JSON into staging tables before applying business logic was the right call. When a COPY failed due to JSONPath mismatches, I could inspect <code>staging_events</code> column metadata and <code>stl_load_errors</code> without corrupting analytics tables.</p>
<h3>Distribution key selection requires data profiling</h3>
<p>I initially considered distributing <code>fact_songplays</code> on <code>user_id</code>, but high-cardinality keys with skewed access patterns can create hot slices. I chose <code>DISTSTYLE AUTO</code> for the fact table and <code>DISTKEY artist_id</code> for songs after analyzing cardinality — letting Redshift optimize where manual tuning had unclear benefit.</p>
<h3>Join logic is the highest-risk transformation</h3>
<p>Linking event logs to song metadata via <code>(song title, artist name)</code> works for this dataset but is fragile in production. A production pipeline would join on stable surrogate keys (<code>song_id</code>) emitted by the application at event time.</p>
<h3>Full reloads are fine until they aren't</h3>
<p>Drop-and-reload simplifies development and guarantees consistency. At scale, I would introduce incremental loads keyed on event timestamp with merge semantics and late-arriving data handling.</p>
<h3>Infrastructure automation saves hours</h3>
<p>Provisioning a Redshift cluster, IAM role, and security group manually is error-prone. Codifying it in <code>redshift_setup.py</code> made teardown and re-creation repeatable — a pattern I'd extend with Terraform for team use.</p>
