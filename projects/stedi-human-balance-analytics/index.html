README

Privacy-Governed IoT Data Lakehouse for Human Balance Analytics

A consent-aware AWS lakehouse pipeline that curates multi-source sensor data for real-time step-detection ML.

Executive Summary

STEDI develops a connected Step Trainer — a hardware device with motion sensors and a companion mobile app — to help users perform balance exercises and detect steps in real time. Early adopters generate three high-volume data streams:

Source Data Sensitivity
Customer registration Profile, device serial number, consent timestamps Contains PII
Mobile accelerometer X/Y/Z motion readings tied to user email Behavioral + identifiable
Step Trainer IoT sensor Distance readings from onboard motion sensor Device-level telemetry

The business challenge is not simply moving data to the cloud — it is building a privacy-first analytics pipeline that:

  1. Keeps raw PII out of downstream analytics and ML workloads
  2. Enforces research consent at the row level, including temporal consent (data collected before consent must be excluded)
  3. Produces a joined, ML-ready feature dataset that aligns accelerometer and Step Trainer readings at the same timestamp

I designed and implemented this project as an AWS lakehouse using a medallion architecture (Landing → Trusted → Curated). The pipeline transforms heterogeneous JSON sources into governed datasets that data scientists can consume directly for step-detection model training — without exposing customer PII or non-consented records.

Value delivered:

  • ✅ Regulatory-aligned data handling through consent-aware filtering
  • ✅ Reusable, cataloged datasets registered in the AWS Glue Data Catalog
  • ✅ Automated PySpark transformations with built-in data quality checks
  • ✅ A single curated table (machine_learning_curated) ready for feature engineering and model training

Data Model

This project implements a lakehouse logical model rather than a traditional OLAP warehouse. Tables are organized by medallion zone and domain, with the final curated output structured for ML feature consumption.

Dimension-Like Tables

Table Grain Description
customer_trusted One row per consented customer Customers who opted into research (shareWithResearchAsOfDate IS NOT NULL)
customer_curated One row per active research participant Distinct customers with verified accelerometer activity — the governed participant population

These tables carry slowly changing consent attributes (research, public, friends sharing dates) that drive downstream filtering logic.

Fact-Like / Event Tables

Table Grain Measures
accelerometer_trusted One row per (user, timestamp) x, y, z accelerometer axes
step_trainer_trusted One row per (serialNumber, sensorReadingTime) distanceFromObject
machine_learning_curated One row per (serialNumber, timestamp) Combined sensor features: distance + x/y/z

Why a Star-Schema–Inspired Design (Without a Traditional Warehouse)

I deliberately chose a lakehouse medallion layout over loading into a columnar warehouse like Redshift because:

  1. Source format — All ingest data arrives as semi-structured JSON; S3 + Glue handles this natively without upfront schema enforcement.
  2. ML consumption pattern — Data scientists need a wide, timestamp-aligned feature table, not normalized dimension lookups at query time.
  3. Privacy boundaries — Zone separation (Landing → Trusted → Curated) provides a clear audit trail for consent enforcement, which is harder to express in a flat star schema alone.
  4. Cost and scale — Serverless Glue + S3 scales with batch volume without provisioning warehouse clusters.

The final machine_learning_curated table behaves like a denormalized fact table at the (device, timestamp) grain — the pattern ML teams typically prefer for training pipelines.

Pipeline Workflow

Five AWS Glue jobs execute sequentially based on data dependencies. Each job reads from the Glue Data Catalog, applies Spark SQL transformations, runs data quality checks, and writes results back to S3 with catalog updates.

Capability Implementation Details

PII minimization ✅ Implemented Trusted-zone jobs drop unnecessary customer attributes before downstream joins
Data validation ✅ Implemented AWS Glue Data Quality EvaluateDataQuality with ColumnCount > 0 on every write node
Catalog synchronization ✅ Implemented Sinks use enableUpdateCatalog=True and updateBehavior="UPDATE_IN_DATABASE"
Scalable architecture ✅ Implemented Serverless Glue + S3 — no cluster provisioning required
Reproducible transforms ✅ Implemented Version-controlled PySpark scripts with explicit Spark SQL
Incremental loading ⏳ Batch full-refresh Current jobs process full datasets; incremental patterns are a planned improvement
Orchestration / scheduling ⏳ Manual triggers Jobs are designed for Glue Studio / scheduled triggers — not yet wired to Airflow
Idempotency ⏳ Partial Full overwrites per run; deduplication applied at customer curated layer

A customer may agree to share data on day 30, but the app may have collected accelerometer readings from day 1. Without temporal filtering (timestamp > shareWithResearchAsOfDate), pre-consent data would leak into the trusted zone.

This design also supports future consent revocation: if a customer withdraws consent, their shareWithResearchAsOfDate boundary remains auditable, and re-running the pipeline excludes post-revocation data that falls outside the original consent window.

Performance Considerations

The current implementation is optimized for correctness and governance on batch workloads. Below is how the architecture handles performance today and where I would invest next.

Area Current State Production Recommendation
Parallel processing PySpark on AWS Glue DPUs Glue auto-scales executors; tune worker type and DPU count based on JSON file volume
Partitioning Not partitioned (partitionKeys=[]) Partition landing/trusted zones by year/month/day derived from timestamp to reduce scan costs
File format JSON (human-readable, schema-flexible) Migrate curated outputs to Parquet or Iceberg for columnar compression and predicate pushdown
Join optimization Spark SQL broadcast/hash joins Pre-filter smaller tables (customer_curated) before joining large sensor streams
Distribution keys N/A (S3 lakehouse) If promoted to Redshift, distribute machine_learning_curated on serialNumber
Sort keys N/A (S3 lakehouse) If promoted to Redshift, sort on timestamp for time-range ML training queries
Query optimization Athena over Glue Catalog Use partition projection and column pruning; consider materialized views for repeated aggregates

The ML curated job joins two time-series tables on exact timestamp equality. At scale, I would:

  1. Repartition both DataFrames by timestamp before the join to reduce shuffle volume
  2. Apply a time-window tolerance if device clock skew exists (not needed in current synthetic data)
  3. Persist intermediate trusted tables in Parquet to avoid re-parsing JSON on every downstream job

Running Locally

This pipeline runs on AWS Glue in the cloud. There is no local Docker stack — deployment follows a standard AWS setup workflow.

Prerequisites

  • AWS account with permissions to create S3 buckets, Glue databases/tables, and run Glue jobs
  • AWS CLI installed and configured
  • An IAM user or role with S3 and Glue access (I used a dedicated IAM user with AmazonS3FullAccess and Glue service permissions)

1. Configure AWS CLI

aws configure
# Enter your Access Key, Secret Key, and default region (e.g., us-east-1)

2. Create an S3 Bucket

aws s3 mb s3://<your-bucket-name>

3. Upload Landing Data

From the repository root:

aws s3 cp ./starter/customer/landing/       s3://<your-bucket-name>/customer/landing/       --recursive
aws s3 cp ./starter/accelerometer/landing/  s3://<your-bucket-name>/accelerometer/landing/  --recursive
aws s3 cp ./starter/step_trainer/landing/   s3://<your-bucket-name>/step_trainer/landing/   --recursive

4. Create Glue Data Catalog Tables

Run the DDL scripts in Athena or the Glue console. Update the LOCATION paths to point to your bucket:

DDL Script Table
starter/customer/ddl/customer_landing.sql customer_landing
starter/accelerometer/ddl/accelerometer_landing.sql accelerometer_landing
starter/step_trainer/ddl/step_trainer_landing.sql step_trainer_landing

5. Deploy and Run Glue Jobs

  1. Open AWS Glue Studio and create a visual ETL job for each script under starter/*/scripts/
  2. Update S3 paths and catalog database/table names in each script to match your environment
  3. Execute jobs in dependency order:
customer_landing_to_trusted
  → accelerometer_landing_to_trusted
  → customer_trusted_to_curated
  → step_trainer_landing_to_trusted
  → step_trainer_trusted_to_machine_learning_curated

6. Validate Output

Query tables in Amazon Athena or inspect outputs in the Glue Data Catalog:

SELECT COUNT(*) FROM machine_learning_curated;
SELECT * FROM machine_learning_curated LIMIT 10;

Lessons Learned

1. Privacy must be encoded in the pipeline, not documented in a policy.

Filtering on shareWithResearchAsOfDate IS NOT NULL is necessary but insufficient. The temporal join condition (timestamp > shareWithResearchAsOfDate) is what prevents pre-consent data leakage. I learned to treat consent as a time-bounded predicate, not a static flag.

2. Medallion zones create clear ownership boundaries.

Separating Landing (raw), Trusted (consent-filtered), and Curated (ML-ready) made it straightforward to explain to stakeholders which datasets are safe for which use cases. The zone naming convention doubles as a data governance API.

3. JSON is great for landing, expensive for everything else.

JSON kept initial ingest simple, but repeated parsing across five jobs adds latency. In a production system, I would convert to Parquet at the Trusted boundary and never re-read JSON downstream.

4. Glue Studio accelerates prototyping; scripts belong in Git.

Visual workflows helped me iterate on join logic quickly, but the exported PySpark scripts in this repository are the source of truth. Keeping them version-controlled enables code review and CI integration.

5. Data quality checks should match business rules, not just schema checks.

The current ColumnCount > 0 rule catches empty writes but not logical errors (e.g., orphaned serial numbers). Expanding rules to validate join cardinality and consent invariants would catch regressions earlier.
