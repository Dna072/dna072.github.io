<p>The business challenge is not simply <em>moving data to the cloud</em> — it is building a <strong>privacy-first analytics pipeline</strong> that:</p>
<ol>
<li>Keeps raw PII out of downstream analytics and ML workloads</li>
<li>Enforces <strong>research consent at the row level</strong>, including temporal consent (data collected <em>before</em> consent must be excluded)</li>
<li>Produces a <strong>joined, ML-ready feature dataset</strong> that aligns accelerometer and Step Trainer readings at the same timestamp</li>
</ol>
<p>I designed and implemented this project as an <strong>AWS lakehouse</strong> using a medallion architecture (Landing → Trusted → Curated). The pipeline transforms heterogeneous JSON sources into governed datasets that data scientists can consume directly for step-detection model training — without exposing customer PII or non-consented records.</p>
<p><strong>Value delivered:</strong></p>
<ul>
<li>✅ Regulatory-aligned data handling through consent-aware filtering</li>
<li>✅ Reusable, cataloged datasets registered in the AWS Glue Data Catalog</li>
<li>✅ Automated PySpark transformations with built-in data quality checks</li>
<li>✅ A single curated table (<code>machine_learning_curated</code>) ready for feature engineering and model training</li>
</ul>

<h3>Why a Star-Schema–Inspired Design (Without a Traditional Warehouse)</h3>
<p>I deliberately chose a <strong>lakehouse medallion layout</strong> over loading into a columnar warehouse like Redshift because:</p>
<ol>
<li><strong>Source format</strong> — All ingest data arrives as semi-structured JSON; S3 + Glue handles this natively without upfront schema enforcement.</li>
<li><strong>ML consumption pattern</strong> — Data scientists need a <strong>wide, timestamp-aligned feature table</strong>, not normalized dimension lookups at query time.</li>
<li><strong>Privacy boundaries</strong> — Zone separation (Landing → Trusted → Curated) provides a clear audit trail for consent enforcement, which is harder to express in a flat star schema alone.</li>
<li><strong>Cost and scale</strong> — Serverless Glue + S3 scales with batch volume without provisioning warehouse clusters.</li>
</ol>
<p>The final <code>machine_learning_curated</code> table behaves like a <strong>denormalized fact table</strong> at the <code>(device, timestamp)</code> grain — the pattern ML teams typically prefer for training pipelines.</p>

<h2>Pipeline Workflow</h2>
<p>Five AWS Glue jobs execute sequentially based on data dependencies. Each job reads from the Glue Data Catalog, applies Spark SQL transformations, runs data quality checks, and writes results back to S3 with catalog updates.</p>
<pre><code class="language-mermaid">flowchart LR
    subgraph Job1["Job 1 — Customer Landing → Trusted"]
        J1A["Read JSON from S3"] --> J1B["Filter: shareWithResearchAsOfDate IS NOT NULL"]
        J1B --> J1C["Write customer_trusted"]
    end

    subgraph Job2["Job 2 — Accelerometer Landing → Trusted"]
        J2A["Join accelerometer_landing ⋈ customer_trusted"] --> J2B["Filter: timestamp > consent date"]
        J2B --> J2C["Drop PII columns"]
        J2C --> J2D["Write accelerometer_trusted"]
    end

    subgraph Job3["Job 3 — Customer Trusted → Curated"]
        J3A["Join customer_trusted ⋈ accelerometer_trusted"] --> J3B["SELECT DISTINCT customer attributes"]
        J3B --> J3C["Write customer_curated"]
    end

    subgraph Job4["Job 4 — Step Trainer Landing → Trusted"]
        J4A["Join step_trainer_landing ⋈ customer_curated"] --> J4B["Filter by serialNumber"]
        J4B --> J4C["Write step_trainer_trusted"]
    end

    subgraph Job5["Job 5 — ML Curated Feature Table"]
        J5A["Join accelerometer_trusted ⋈ step_trainer_trusted"] --> J5B["Align on timestamp"]

<h2>Lessons Learned</h2>
<p><strong>1. Privacy must be encoded in the pipeline, not documented in a policy.</strong></p>
<p>Filtering on <code>shareWithResearchAsOfDate IS NOT NULL</code> is necessary but insufficient. The temporal join condition (<code>timestamp > shareWithResearchAsOfDate</code>) is what prevents pre-consent data leakage. I learned to treat consent as a <strong>time-bounded predicate</strong>, not a static flag.</p>
<p><strong>2. Medallion zones create clear ownership boundaries.</strong></p>
<p>Separating Landing (raw), Trusted (consent-filtered), and Curated (ML-ready) made it straightforward to explain to stakeholders which datasets are safe for which use cases. The zone naming convention doubles as a data governance API.</p>
<p><strong>3. JSON is great for landing, expensive for everything else.</strong></p>
<p>JSON kept initial ingest simple, but repeated parsing across five jobs adds latency. In a production system, I would convert to Parquet at the Trusted boundary and never re-read JSON downstream.</p>
<p><strong>4. Glue Studio accelerates prototyping; scripts belong in Git.</strong></p>
<p>Visual workflows helped me iterate on join logic quickly, but the exported PySpark scripts in this repository are the source of truth. Keeping them version-controlled enables code review and CI integration.</p>
<p><strong>5. Data quality checks should match business rules, not just schema checks.</strong></p>
<p>The current <code>ColumnCount > 0</code> rule catches empty writes but not logical errors (e.g., orphaned serial numbers). Expanding rules to validate join cardinality and consent invariants would catch regressions earlier.</p>
