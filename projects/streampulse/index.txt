1e:T4822,<h1>StreamPulse — Video Analytics &#x26; Performance Dashboard</h1>
<p>A production-style analytics product for video content: a <strong>FastAPI</strong> backend that
serves aggregated metrics straight from PostgreSQL, and a polished <strong>React +
TypeScript</strong> dashboard that renders them. Every chart is fed by a real API call —
<strong>nothing is hardcoded in the UI</strong>.</p>
<blockquote>
<p><strong>Honesty note:</strong> this is a portfolio project. All data is <strong>synthetic</strong>, produced
by a seed script (<code>app/seed.py</code>). There are no real users, no real traffic, and no
uptime/revenue claims anywhere.</p>
</blockquote>
<p>Built by <strong>Derrick Adjei</strong> as part of a media-technology portfolio (targeting
Backlight — Junior Fullstack, backend focus).</p>

engagement rate, completion rate — each with an optional period-over-period delta.</li>
<li><strong>Time series</strong> — views / watch-hours / unique-viewers over time with automatic
day/week/month bucketing and an overlaid <em>previous period</em> line in comparison mode.</li>
<li><strong>Engagement funnel</strong> — impressions → views → 25% → 50% → 75% → completion, with
per-step conversion.</li>
<li><strong>Audience breakdowns</strong> — top countries and device-type split.</li>
<li><strong>Video performance</strong> — paginated, sortable per-video table.</li>
<li><strong>Filters</strong> — date range (quick presets + custom), single-video filter, comparison
toggle. All filters flow to every endpoint.</li>
<li><strong>UX states</strong> — every panel has loading (skeleton), error (with retry), and empty
states.</li>
</ul>
<hr>
<h2>Architecture</h2>
<pre><code class="language-mermaid">flowchart LR
    subgraph Browser
      UI["React + TS SPA&#x3C;br/>(Vite, Recharts, React Query)"]
    end
    subgraph Edge
      NX["nginx&#x3C;br/>(serves built SPA)"]
    end
    subgraph API["FastAPI service"]
      MW["Request-ID + structured logging&#x3C;br/>middleware"]
      AUTH["JWT auth&#x3C;br/>(OAuth2 password flow)"]
      AN["Analytics routers&#x3C;br/>(aggregation queries)"]
    end
    DB[("PostgreSQL 16&#x3C;br/>videos · impression_events · view_events")]

    UI -->|"/api/v1/* (Bearer JWT)"| API
    NX --- UI
    MW --> AUTH --> AN
    AN -->|"date_trunc, count(distinct),&#x3C;br/>conditional aggregation"| DB
</code></pre>
<p>Request flow: the SPA authenticates via <code>/api/v1/auth/login</code>, stores the JWT, and
attaches it to every request. The API validates the token, resolves the shared
date-range/comparison filter, runs a bounded aggregation query, and returns a small
reduced payload. PostgreSQL does the heavy lifting; the API ships only summarized data.</p>

<h2>Data model</h2>
<p>Two append-only <strong>fact</strong> tables around a <code>videos</code> <strong>dimension</strong> table:</p>
<ul>
<li><strong><code>videos</code></strong> — one row per piece of content (title, category, duration, publish date).</li>
<li><strong><code>impression_events</code></strong> — a video was surfaced to a viewer (top of the funnel).</li>
<li><strong><code>view_events</code></strong> — a viewer started watching. Carries <code>watch_seconds</code>,
<code>quartile_reached</code> (0–4 → highest 25% milestone reached), engagement flags
(<code>liked</code>/<code>commented</code>/<code>shared</code>), a pseudonymous <code>viewer_id</code> (for unique-viewer counts),
and <code>country_code</code> / <code>device_type</code> dimensions.</li>
</ul>
<p>Splitting impressions from views keeps the common "views" queries scanning a smaller
table, while still supporting a true impressions-based funnel.</p>
<hr>
<h2>Database &#x26; indexing — the <em>why</em></h2>
<p>Every dashboard query is an <strong>aggregation over a time window</strong>, optionally narrowed by
video, and often grouped by a dimension (country/device). The indexes are chosen to
serve exactly those access patterns.</p>
<table>
<thead>
<tr>

<th>Columns</th>

</tr>
</thead>
<tbody>

<td><code>(event_time)</code></td>
<td>Every time-bounded query</td>
<td>The date range is present in <em>all</em> dashboard queries, so a leading <code>event_time</code> index bounds every scan.</td>

<h3>Proof: the planner uses them</h3>
<p>Time-series over a 30-day window (82k-view seed) — bounded by <code>ix_views_time</code>:</p>
<pre><code>GroupAggregate
  ->  Sort  (Sort Key: date_trunc('day', event_time))
        ->  Index Scan using ix_views_time on view_events
              Index Cond: ((event_time >= now() - '30 days') AND (event_time &#x3C; now()))
</code></pre>
<p>Per-video + date range — resolved by the composite <code>ix_views_video_time</code>:</p>
<pre><code>Aggregate
  ->  Bitmap Heap Scan on view_events
        ->  Bitmap Index Scan on ix_views_video_time
              Index Cond: ((video_id = 5) AND (event_time >= …) AND (event_time &#x3C; …))
</code></pre>
<h3>Scaling further (documented, not built)</h3>
<p>For very large, append-only event tables the next steps would be <strong>native range
partitioning by month</strong> on <code>event_time</code> (partition pruning + cheap retention drops)
and a <strong>BRIN index</strong> on <code>event_time</code> (tiny, ideal for time-ordered inserts). Heavy
dashboards would then read from <strong>pre-aggregated daily rollup tables</strong> refreshed by a
scheduled job, rather than scanning raw events on every request.</p>
<hr>
<h2>Query design</h2>
<ul>
<li><strong><code>date_trunc(granularity, event_time)</code></strong> for time bucketing, with granularity chosen
automatically from the window length (≤31d → day, ≤120d → week, else month).</li>
<li><strong><code>count(DISTINCT viewer_id)</code></strong> for unique viewers.</li>
<li><strong>Conditional aggregation</strong> (<code>avg</code>/<code>sum</code> over <code>CASE</code> expressions) computes engagement
rate, completion rate, and all funnel quartiles in a <strong>single table scan</strong> each,
instead of multiple round-trips.</li>
<li>Every query is <strong>bounded by <code>event_time</code></strong> so the indexes above apply.</li>
</ul>
<hr>
<h2>Comparison mode</h2>
<p>When <code>compare=true</code>, the API computes the <strong>immediately preceding, equal-length window</strong>
(<code>[start - span, start)</code>). Overview KPIs return <code>{ value, previous, delta_pct }</code>; the
time series returns a parallel <code>previous_points</code> array aligned by index so the UI can
overlay it as a dashed line.</p>
<hr>
<h2>Seed data</h2>
<p><code>app/seed.py</code> generates months of plausible-but-synthetic events:</p>
<ul>
<li>24 videos across 6 categories with per-video <strong>popularity</strong> and <strong>quality</strong> traits.</li>
<li><strong>Recency decay</strong> (interest fades after publish) and <strong>weekly seasonality</strong> (weekends
run hotter), plus a mild upward trend.</li>
<li><strong>Impression → view</strong> click-through, then per-view <strong>retention</strong> sampled from a
quality-shifted distribution (TV/desktop watch slightly longer than mobile).</li>
<li>A bounded <strong>viewer pool</strong> with a "power viewer" subset, so unique viewers are
meaningfully fewer than total views.</li>
</ul>
<p>Reproducible via <code>SEED_RANDOM_SEED</code>. Volume via <code>SEED_DAYS</code> / <code>SEED_TRAFFIC</code>.</p>

<h2>AWS deployment notes</h2>
<p>A pragmatic path to production (architecture only — no live infra is provisioned):</p>
<pre><code class="language-mermaid">flowchart LR
    U[Users] --> CF[CloudFront]
    CF --> S3[(S3 static SPA)]
    CF --> ALB[Application Load Balancer]
    ALB --> ECS["ECS Fargate&#x3C;br/>FastAPI tasks (autoscaled)"]
    ECS --> RDS[(RDS PostgreSQL&#x3C;br/>Multi-AZ)]
    ECS --> CW[CloudWatch Logs/Alarms]
</code></pre>
<ul>
<li><strong>Frontend:</strong> build the SPA and host on <strong>S3</strong> behind <strong>CloudFront</strong> (CDN + TLS).</li>
<li><strong>API:</strong> container image on <strong>ECS Fargate</strong> behind an <strong>ALB</strong>, using the <code>/health</code> and
<code>/ready</code> probes for target-group health and autoscaling.</li>
<li><strong>Database:</strong> <strong>RDS for PostgreSQL</strong> (Multi-AZ for availability); credentials in
<strong>Secrets Manager</strong>, injected as env vars; <code>SECRET_KEY</code> likewise.</li>
<li><strong>Migrations:</strong> run <code>alembic upgrade head</code> as a one-off ECS task in the deploy
pipeline before shifting traffic.</li>
<li><strong>Logs/metrics:</strong> ship structured logs to <strong>CloudWatch</strong> (request IDs make tracing a
single request across log lines trivial); alarm on 5xx rate and DB connections.</li>
<li><strong>Scale:</strong> as event volume grows, add read replicas, monthly partitioning, and daily
rollup tables (see <a href="#scaling-further-documented-not-built">scaling notes</a>).</li>
</ul>
